## Operating model

**The governor is the review lane, not the agent fleet.** Concurrency is 10 and `AI Ready` is empty
while `AI Review` holds 30 — the fleet is starved at the front and jammed at the back. Adding agents
adds nothing until the review lane drains. Every rule below exists to protect that lane.

### Lane contract — one owner per lane

| Lane | Owner | Exit condition |
|---|---|---|
| Backlog | human | triaged + labelled `ai:yes` / `ai:no` / `ai:needs-spec` |
| AI Ready | dispatcher | claimed (only refilled while `AI Review` < cap) |
| AI Processing | worker | PR pushed, self-audit passed |
| AI Review | **controller (me)** | risk gate passed → merged to `staging` |
| Deployed to Staging | controller | API smoke green against staging |
| Deployed to Prod | controller | staging→main train shipped + prod smoke green |
| AI Awaiting Input / AI Blocked | human | question answered → back to AI Ready |

### Risk classes — what "reviewed" means

| Class | What it is | Gate |
|---|---|---|
| **A** | dependabot, lockfiles, docs-only | green checks → **auto-merge, no human read** |
| **B** | one service, no schema/infra, ≤30 files | `/review` + I check the diff against the ticket's acceptance criteria |
| **C** | migrations, terraform/helm, CI workflows, auth/tenant/billing/secrets, >30 files | `/review` + `/security-review` + staging deploy + API smoke **before** merge |

Class is auto-assigned by `tools/board.py`; override in the Decisions log with a reason.

### The intent check (the part a linter cannot do)

For every B and C PR I read the **ticket** first, then the diff, and answer three questions in the
Linear comment before merging:
1. Does the diff satisfy every acceptance criterion — not a subset that makes tests pass?
2. Does it solve the problem the ticket was *filed about*, or the narrower one that was easy?
3. What did it change that the ticket did not ask for?

Anything that fails (1) or (2) goes back to `AI Ready` with the gap named — not merged with a caveat.

### Which tickets agents can take

`ai:yes` — all four must hold:
- acceptance criteria are checkable in-repo or on staging (test, query, log, endpoint),
- no prod write and no `main` merge needed,
- blast radius ≤ 1 service (or a `[FOUNDATION]` ticket that explicitly owns the shared surface),
- no open product judgment call.

`ai:needs-spec` — good ticket, criteria too vague to verify. Sharpen, then re-label.
`ai:no` — product/pricing/UX judgment, prod-only ops, cross-team coordination, anything needing a
human decision mid-flight.

### Post-deploy verification

`.github/scripts/spec_smoke.py` + `seams.sh` (env files for staging/prod already exist) is the API
test surface. Staging merge → smoke → `Deployed to Staging`. The staging→main train runs on a batch,
never per-PR; prod smoke green → `Deployed to Prod` → `Done`.
